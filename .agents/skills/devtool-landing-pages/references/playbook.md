# Landing pages playbook

## Fictional product context

TraceNest is a fictional local HTTP replay tool. An engineer can replay a sanitized fixture locally, but service integration needs a platform owner. Sample replay is not proof of recurring project value. Do not invent hosted behavior, speed improvements, or customer results.

## Decision to resolve

Organize the page around task, supported stack, input/output, runnable path, integration limits, proof, and adoption requirements. Provide an evaluator route and a platform/buyer route where they need different evidence.

## Task-specific method

Make the working example, docs, repository where applicable, integration requirements, and local versus hosted boundary visible. A signup gate before any product evidence may be the wrong path.

## Worked application

For this scenario, apply the task-specific method above and deliver: An annotated page outline or implementation, section-level proof requirements, CTA behavior, and a measurement plan connecting the page to evaluation quality.

Do not assume missing capabilities or report proposed tests as completed. A useful answer identifies what is known, finishes the requested artifact within that scope, and names the next bounded verification when needed.

## Review criteria

Do not promise conversion lifts from a wireframe. A demo request, documentation visit, and successful evaluation are different events.

The [shared method examples](shared-methods.md) provide additional templates and cross-product examples; apply only those that fit the product scope.
